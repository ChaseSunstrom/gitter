**Verdict: changes needed.** I found no CRITICAL issues. The MEDIUM issues below affect co-author credit, session consistency, input handling and memory. I couldn't run `cargo test`, so I verified each finding by reading the code. Where a claim depends on a dependency's behaviour, I checked its source.

## lens: maintainer

- MEDIUM — src/api/collab.rs:472-483 and :253 — Co-author credit is lost when a person's last stream closes. `Watching::drop` removes the `Person`, which discards `typed`. `state()` builds `co_authors` only from `people` where `typed` is true. Reproducer: nina joins and types, then closes her tab or her stream reconnects. Alice, who joined later or whose client reset on a reconnect `init`, commits with no `Co-authored-by: nina`. That breaks the README claim "credits everyone who typed". The same applies to a Lagged `resync`, which ends the stream. Fix: keep a session-level `authors: HashMap<i64, String>` filled in `change` and build `co_authors` from it. Add a test for type, drop the stream, then check `co_authors`. Confidence: high.
- MEDIUM — src/api/collab.rs:285-286 — The co-author trailer is built from `display_name` with no sanitising. `update_me` only trims and limits length (account.rs:312-319). A display name of `"N\nCo-authored-by: Mallory <m@x>"` puts a forged trailer line into someone else's commit message. `releases.rs:330` already strips `<>\r\n\0` from the name. Fix: reuse that filter (or lift it into a helper next to `User::signature`) and add a test. Confidence: high.
- MEDIUM — src/api/collab.rs:340-358 (check at 306-317) — Two simultaneous joins can create two sessions for one file. `found` is computed and the `SESSIONS` lock released. The `.await`s on `resolve`, `ls-tree` and `blob` follow. The lock is then re-taken and the new session inserted without looking again. Reproducer: fire two `POST /collab` for the same branch and path at once, and the ids differ. The two people then edit separate copies without knowing. This is likely when an invite link is opened by several people together. Fix: re-run the find under the second lock and return the existing session. Confidence: high.
- MEDIUM — src/api/collab.rs:433-447 and src/api/mod.rs:417-420 — `presence` has no limiter. The comment at collab.rs:386 and `is_collab_typing` both say ops and presence have "their own budget", but only `change` checks `st.limiter`. Presence is also exempt from the write allowance. One writer looping `POST …/presence` floods the 256-slot broadcast channel. Every other stream then gets Lagged, a `resync` and a dropped stream. Fix: call `st.limiter.check` in `presence`, using its own key such as `collab-presence:{uid}`. Confidence: high.
- MEDIUM — src/api/collab.rs:384-414 — The history is bounded by op count (`HISTORY`=1000), not by size. The check at line 406 only limits the resulting text. Reproducer: a writer sends `[-N, "<1M chars>"]` repeatedly. Each op stays under `MAX_TEXT`, the global body limit is 40 MB (mod.rs:338), and 900 ops per minute are allowed. That retains about 2 MB × 1000 per session, across up to 200 sessions. Fix: cap the summed insert length of `history` (drop the oldest entries beyond a few MB) or cap the size of a single op. Confidence: medium-high.
- MEDIUM — static/js/ot.js:`diff` (`push(op, now.slice(...))`), static/js/collab.js:53-55 and src/api/collab.rs:92-107 — `diff` works on UTF-16 units, so it can split a surrogate pair. Replacing 😀 with 😁 gives `[…, -1, "\ude01", …]`, a lone surrogate. serde_json rejects lone surrogates (serde_json-1.0.154 `read.rs:962-964`, `LoneLeadingSurrogateInHexEscape`), so the request fails. `sendOp` then calls `resync`, which replaces the local text with the server's and discards the user's edit. Neither the Rust tests nor `ot-check.mjs` go through JSON, so they miss it. Fix: move the `diff` boundaries off pair halves (back up while `old[p-1]` is a high surrogate, and likewise for the suffix). Add a node test that round-trips `JSON.stringify` of the op. Confidence: high.
- MEDIUM — src/api/collab.rs:98-100 with 55 and 87 — `parse` turns any positive i64 into `usize`, and adjacent counts are summed with `+=`. Release builds don't set `overflow-checks` (Cargo.toml:39-42), so the sum wraps. The op `[9223372036854775808-sized parts, "x", …]` can be built so `base_len` wraps to the document length (for example `Retain(2^63)`, an insert, then `Retain(2^63+6)` on a 6-unit text). `apply` then slices `doc[at..at+n]` out of range and panics while holding the session lock. A debug build panics earlier, on the overflow itself. Fix: use `checked_add`/`saturating_add` in `Build` and `base_len`, or reject any count above `MAX_TEXT` in `parse`. Confidence: high.
- LOW — static/js/pages/pages/editor.js:223 with static/js/collab.js:40-46 — Clicking "Edit together" after typing replaces the textarea with the server text (`reset` → `setText`), silently losing unsaved edits. Fix: send `diff(joined.text, ta.value)` as the first op, or confirm first. Confidence: medium.
- LOW — src/api/collab.rs:300-365 and :279-288 — `join` and `presence` call `enter`, which adds a `Person` with `streams: 0` and no stream. A late `presence` POST after the stream closed, or a join that never opens a stream, leaves a ghost person who is never removed. The ghost also takes one of the 20 slots. Fix: only create people in `events`, or expire people with `streams == 0` after a short grace period. Confidence: medium.
- LOW — src/api/mod.rs:415-421 — The `is_collab_typing` doc comment was inserted into `is_view_count`'s comment block. `is_view_count` now has no doc and the traffic comment sits above the collab function. Also, no test covers the new write-allowance exemption or the 900-per-minute limit. Fix: move the comment and add a test next to the existing rate-limit tests. Confidence: high.
- LOW — src/api/collab.rs:272 — The `session()` doc says "for someone who can write to it", but the function doesn't check that. Callers do. `events` checks only at connect time, so a collaborator removed afterwards keeps streaming. Fix: fix the comment, and optionally drop the stream when the check fails. Confidence: medium.
